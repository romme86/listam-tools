## What the research changed

Autobase **7.28.2**, Hyperswarm **4.17.1**, Hypercore **11.36.1** and Corestore
**7.12.5** are aligned across the four active runtime graphs. HyperDHT **6.34.0**,
udx-native **1.21.1** and blind-relay **1.6.1** were retained. Relay selection
starts randomly and cycles through configured candidates on fallback attempts.
Blind-storage and owner-control paths now receive the same relay configuration.

Authenticated list-data mirroring now persists both sides of the subscription:
participants publish revisioned manifests containing public base/system/view/
writer core keys; helpers validate the authenticated device scope, reject
stale/conflicting revisions, and persist before acknowledging. Historical
writer keys are retained in the manifest union. Reconciliation, retries,
withdrawal and restart restoration are bounded. Helpers receive no list
plaintext or encryption keys. Withdrawal stops active downloads while keeping
already stored ciphertext.

The headless archive vendors the exact shared packages, so it installs without
unpublished npm versions or sibling workspace paths. Extract it, enter
`package/`, then run `npm install --omit=dev`. Installing the outer tarball from
another directory is not the supported path because the vendored references
are relative. The `--registry` distribution mode remains available for a later
npm release. No npm package was published in this rollout.

## Pi participant recovery

The pre-update status had been stale since 7 September and its 1 GiB quota was
exceeded. With the updated stack, public replication found conflicting signed
history in the Pi's own writer (discovery fingerprint `dc6cb81e…a7224a85`). The
exact origin of that fork was not established; it must not be described as a
proven dependency regression or silently "repaired" by deleting history.

The original store was opened without public replication and exported:
**194 durable records / 66 user items**. The Geekom export contained **204**
durable records. Every user item in the Pi export exists on the Geekom; the
only missing record is an old peer label. Nine differing plan/todo records
have newer timestamps on Geekom. The stale export was not imported over newer
edits.

The full pre-deployment backup remains at
`~/listam-release-backups/2026-09-13/participant/`. The conflicting working
store remains intact at `~/listam-data-conflict-20260913/`, mode 0700. The
owner-only offline export is
`~/listam-release-backups/2026-09-13/pi-offline-export.json`. No historical
store or list item was deleted.

A fresh participant store at `~/listam-data` rejoined the same authorized
project using a new writer identity. Its service control identity was retained,
as was the completely separate connection-relay identity. The quota is 2 GiB.
After history replay, the new participant was authorized and writable but its
projection lacked historical records. Comparison with a fresh Geekom export
found **95 personal-project records** to restore, including **14 user items**;
existing content matched when transport `op`/`version` fields were excluded.
These missing records were restored through the normal authenticated update
path. An initial attempt including three shared-list items was refused before
writing anything because that separate list is read-only on the Pi. Its three
items arrived through the existing read credentials and a read-only snapshot
refresh. No shared-list write permissions were expanded.

Fresh exports then matched for **all 205 durable records and all 72 user items**:
zero missing, differing or additional records after excluding transport
`op`/`version` fields. The original Pi export was never imported over newer
Geekom edits. Recovery exports and the exact missing-record input remain
owner-only in the dated backup directory.

The Pi was restarted after recovery. It returned to **72 user items**, two
peers, the same new writer identity and an authorized, writable state with the
correct current epoch key. Its post-restart export again matched all **205**
records against a fresh Geekom export after excluding protocol/routing
decorations (`op`, `version`, `baseKey`). The diagnostic output override was
removed and its owner-only log archived in the backup directory. Both relay
seeds and both participant control identities still match the pre-deployment
backups. Both relays, both health timers and the Geekom app mirror are active.

Recovery also tried a bounded Autobase batching window and checked
fast-forward hints from the Geekom. The checkpoint requests timed out; the
Geekom's latest system core had a durable length equal to its manifest
prologue. No signatures or encryption checks were bypassed. A temporary
loopback-only replication bridge carried encrypted Hypercore traffic over
the existing SSH access between the two authorized participants, then closed.
History replay completed; batching is back to its default, the temporary
bridge is closed, and neither host has the debug listener open.

## Deferred work and practical limits

- npm publication is explicitly deferred by the operator; native/Pear bundles
  and the self-contained headless archive already contain the shared source.
- Two headless Linux private-network checks remain failing as described above.
  They were not skipped, reclassified as passing or hidden by retries.
- Latest-block catch-up tuning remains off; no performance benefit is claimed.
  Autobee migration, push delivery, notification balancing and unreleased
  native transport patches remain separate research work.
- The physical Wi-Fi/offline/cellular matrix, 16 KB Android runtime,
  store-install upgrade and purchase/restore checks were not repeated for
  these native builds. The extended loss/jitter/MTU benchmark remains open.
- Apple warned that some vendor dSYMs are missing, limiting native crash
  symbolication for those libraries; upload itself succeeded.
- Two earlier Windows builds failed while decoding the publisher's accented
  name; the first UTF-8 pragma change alone did not fix the LLVM resource
  compiler. The final wide-string escape build passed and was published.
